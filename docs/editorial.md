# Editorial workflows

How to add or correct **data** in Urbanist Atlas — orgs, regions, MSA
overrides. Code/contract changes flow through the normal PR review;
this file is the operator guide for the editorial side.

All edits flow through git (no admin UI yet); changes ship via merge
to `main` + `just fly-loaddata`. Auto-deploy ships the *code* that
references the seed; the seed itself is reloaded manually so a
malformed file can't block a code deploy. See
[`docs/deploy.md`](./deploy.md) § Deploys for the full deploy
contract.

## Add or correct an organization

1. Edit [`api/seed/orgs.toml`](../api/seed/orgs.toml). Each entry uses
   the same shape — copy an existing row as a template. Attach to one
   or more regions via stable slugs in the `regions` array (e.g.
   `regions = ["nyc", "nyc-tristate"]`). The slugs must already exist
   in one of the `regions_*.toml` files.
2. Reload locally and exercise:

   ```sh
   just pg-reset && just pg-up        # fresh dev DB
   just migrate-up                    # apply schema
   just loaddata                      # regions → postal → orgs
   just api-run                       # in another shell
   just lookup <postal_code>          # exercise the change
   ```

3. Commit, open a PR, merge. The `deploy-api` job auto-ships the
   code; seed data is *not* auto-applied.
4. **Required post-merge:** `just fly-loaddata`. Loaders upsert by
   stable key, so a re-run converges rather than duplicates.

If you're adding an org for an area that has no leaf region yet, add
the leaf first (see below) and merge that PR before the org PR — or
attach the org to the next-smallest existing region (MSA, county,
state) as a stopgap. The smallest-anchor rule in
[`docs/superpowers/specs/2026-05-19-postal-coverage-design.md`](./superpowers/specs/2026-05-19-postal-coverage-design.md)
explains the trade-off.

## Add a city / county / borough leaf region

1. Edit `api/seed/regions_<cc>.toml` (US:
   [`regions_us.toml`](../api/seed/regions_us.toml); CA:
   [`regions_ca.toml`](../api/seed/regions_ca.toml)). Conventions:
   - Slugs are lowercase ASCII with hyphens.
   - State edges live on the **leaf**, not on the metro.
   - Multi-state / federation regions parent the metro or the leaf,
     not the state.
   - See [`docs/region-graph.md`](./region-graph.md) § Modeling
     conventions for the full rules + worked examples.
2. If the new leaf should be the anchor for a set of postal codes,
   confirm `api/seed/postal_codes_<cc>.csv` points at the new slug
   for those rows. ETL-regenerated postal-code files: see
   `regions_us_msa_overrides.toml` workflow below — the overrides
   feed into the ETL, which re-anchors postal codes via the
   smallest-anchor algorithm.
3. Reload locally as in the org flow above:

   ```sh
   just pg-reset && just pg-up
   just migrate-up
   just loaddata
   just lookup <postal_code>   # confirm the new leaf surfaces
   ```

4. Commit, PR, merge.
5. **Required post-merge:** `just fly-loaddata`.

## Override an MSA / CMA region slug, name, or parents

MSA (US) and CMA (CA) rows are generated by the ETL pipeline from
Census + StatsCan delineation files, so don't hand-edit
`regions_us_msas.toml` or `regions_ca_cmas.toml` — they'll be
regenerated on the next ETL run and your edit will vanish.

**US (CBSA-keyed editorial overrides):**

1. Edit
   [`api/seed/regions_us_msa_overrides.toml`](../api/seed/regions_us_msa_overrides.toml).
   Each row pins a friendly slug + name to a Census CBSA code.
2. Regenerate the canonical MSA file from the staged upstream
   sources:

   ```sh
   urbanist-atlas-server etl regenerate --country=US
   # or via just: just etl-regenerate US
   ```

3. Review the diff in `api/seed/regions_us_msas.toml` (and any
   postal-code re-anchoring in `api/seed/postal_codes_us.csv`).
   Diffs should be small and signal-rich.
4. Commit both the override edit and the regenerated outputs in
   the same PR.
5. **Required post-merge:** `just fly-loaddata`.

**CA (kind + slug overrides in code):**

1. Edit the mapping table at
   [`api/internal/etl/ca/mappings.go`](../api/internal/etl/ca/mappings.go).
   This is Go code, not TOML — slug + kind + parent edges for the
   well-known CMAs (`toronto-cma`, `montreal-cma`, `metro-vancouver`,
   `ottawa-gatineau-cma`).
2. Regenerate:

   ```sh
   just etl-regenerate CA
   ```

3. Review and commit the regenerated `regions_ca_cmas.toml` +
   `postal_codes_ca.csv` outputs alongside the code change.
4. **Required post-merge:** `just fly-loaddata`.

ETL is deterministic — same upstream vintage produces byte-identical
output. If you see noise in the diff that you didn't expect, the
upstream source vintage probably changed; check
[`etl/SOURCES.md`](../etl/SOURCES.md) and run with the pinned
vintage rather than refreshing sources in the same PR.

## Refreshing upstream ETL sources

Only when bumping Census / StatsCan / HUD vintages — not the
common case. Source files live under `etl/sources/<cc>/` (gitignored).

```sh
mise install
pip install -r etl/scripts/requirements.txt   # one-time, for US xlsx→csv
just etl-download US                          # or CA
just etl-regenerate US
```

Then commit the seed-file diffs (not the upstream sources) and run
`just fly-loaddata` post-merge as usual. Bump
[`etl/SOURCES.md`](../etl/SOURCES.md) with the new vintage's
checksums in the same PR.

## Adding a new country

Out of scope until v1.1+. US + CA are the only shipping countries in
v1; PT seed files exist as a multi-parent DAG validation fixture but
are no longer loaded by the user-facing `loaddata` pipeline. To
re-enable PT (or add ES / MX / NL / UK) when editorial coverage is
ready, see
[`docs/region-graph.md`](./region-graph.md) § Adding a new country,
[`api/seed/README.md`](../api/seed/README.md), and the relevant
design spec under `docs/superpowers/specs/`. Coordinate with the
maintainer before opening the PR — country bring-up is a multi-slice
project, not a single PR.
